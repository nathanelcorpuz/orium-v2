### Bug #24 - Signup's 6-digit-code email also carries a working confirmation link, defeating the point of a typed code
- **Reproduce**: sign up for a new account, look at the confirmation email.
- **Reported** by the user 2026-08-04 (REMINDER.md): "the sign up flow asks for a 6 digit code but it still sends a confirmation email."
- **Root cause, confirmed in code**: `signup()` (`src/app/auth/actions.ts`) still passes `emailRedirectTo` on every `supabase.auth.signUp()` call, and its own comment (lines 34-38) says this is deliberate - *if* the Supabase dashboard's "Confirm signup" email template still contains `{{ .ConfirmationURL }}` alongside `{{ .Token }}`, the link keeps working via `/auth/callback` as a fallback. T132 (SPEC.md Phase 17) built the typed-code flow (`verifySignupOtp`) but this is the piece that was never finished - whichever email template is actually configured for "Confirm signup" in the Supabase dashboard evidently still includes the link text/button, not just the code.
- **Expected**: the confirmation email shows only the 6-digit code - no clickable link, matching what T132 set out to build.
- **Not fixable from here**: this is a **Supabase Auth email template**, a dashboard-only setting - no migration, code change, or available Supabase MCP tool (`apply_migration`/`execute_sql`/etc. cover the database, not Auth email templates) can edit it. **Manual step needed from the user**: open the Supabase dashboard → Authentication → Email Templates → "Confirm signup," and remove the `{{ .ConfirmationURL }}` link/button from the template body, leaving only `{{ .Token }}`. Once that's done, `emailRedirectTo` in `signup()` becomes genuinely dead code and can be deleted in a follow-up - left in place for now since removing it before the template is fixed would leave no fallback if the template edit is delayed.

### Bug #27 - Accounts page's monthly breakdown never accounted for income-linked budgets, overstating an income's net contribution to its own account
- **Reproduce**: link an income to an account, then link one or more budgets to that same income. Open the Accounts page and check that account's monthly received/net figures.
- **Reported** by the user 2026-08-04: "Wise Nanay at the moment shows I have a 44k/mo net in the accounts page, but this is not true. Those 44k goes to my budgets. This is a bug. The budgets should be taken into account in this calculation."
- **Confirmed exactly against real production data**: "Nanay - TNIT" (Wise Nanay's linked income, weekly, ₱21,000/week) funds 6 budgets (Gas, Grocery, Laundry, Orius Needs, Food, Leisure) totalling ₱11,000/week in allocations - ₱11,000 × 4 (the weekly-to-monthly multiplier `monthlyEquivalent` already uses) = **₱44,000.00/mo**, the exact figure reported.
- **Root cause**: `computeAccountMonthlyBreakdown` (`src/lib/accountMonthlyBreakdown.ts`, T236) never had any concept of budgets at all - it only ever looked at `recurringItems`/`oneOffItems`/`income_auto_moves`. But an income-linked budget's replenishment nets straight out of the income's own connected account at settle time (T151/Bug #14 - `settleOccurrence` applies `actualAmount - totalAllocation` in a single write, never the raw income amount), and the forecast engine projects that same deduction (Phase 11/T59) - so the account's *true* monthly net was always lower than this breakdown showed, by however much the account's own income funds in budgets. Same shape as the auto-move gap this exact function already had (T236's own 2026-08-03 follow-up) - budgets were simply the next silent money movement this breakdown didn't know about.
- **Expected**: an income-linked budget's monthly allocation is subtracted from its linked income's own connected account, the same way an auto-move already is.
- **Fixed by**: `computeAccountMonthlyBreakdown` gains a `budgets` parameter (a minimal `BudgetFundingItem` shape: id/name/allocation/linkedIncomeId/active) - for each active, income-linked budget whose linked income is connected to the account being computed, its allocation's monthly-equivalent (using the *linked income's* recurrence rule, same reasoning `autoMoves` already uses - a budget replenishment has no schedule of its own when income-linked) is subtracted from `monthlyDeducted` and surfaced as its own transparent "Funds budgets" line in the expanded breakdown, mirroring the existing "Auto-moves" section exactly. An own-schedule budget (no `linkedIncomeId`) is correctly left alone - `settleBudgetReplenish` never touches a main account at all, confirmed in code (`forecast/actions.ts`'s own comment: "never touches a main [account]"). `accounts/page.tsx` passes `forecastData.budgets` (already fetched by the existing `loadForecast()` call, no new query), filtered to exclude scenario-merged budgets (`fromScenario`) since those aren't real money. 281/281 tests (5 new: the basic subtraction, an own-schedule budget being a no-op, a switched-off budget, a switched-off linked income, and an account the linked income isn't connected to), tsc, build, eslint clean.

### Bug #26 - Every deployment since T239 shipped had been silently rejected by Vercel, leaving production on a stale build
- **Reproduce**: check the Vercel dashboard's Deployments list against `git log origin/main`.
- **Found** 2026-08-04, after the user reported this session's Bug #22/#23 fixes weren't visible in production despite a confirmed successful `git push` to `origin/main`. The GitHub check on the pushed commit read "All checks have failed - Vercel: Deployment failed," and its own "Details" link pointed at Vercel's cron-jobs and functions pricing docs - Vercel's own explanation for the failure, not a random page.
- **Root cause**: `vercel.json` (added by T239, SPEC.md Phase 42) scheduled the daily-notifications cron at `*/15 * * * *` (every 15 minutes) - matching the "20-minute window, wide enough to absorb normal cron jitter against the 15-minute check interval" design T239's own write-up describes. **Vercel's free Hobby plan only allows a cron job to run once per day** - a plan limit T239 was never checked against. Every deployment carrying that config had been rejected outright since it first landed, silently: nothing in that session's process surfaces a rejected Vercel deployment (`npm run build` succeeds fine locally - Vercel's own build step never even runs when the *pre-build* plan-limit check fails first), so it went unnoticed. Production had been running whatever the last commit *before* T239 was, for as long as that was true - since T239 shipped on 2026-08-03, discovered here on 2026-08-04.
- **Expected**: a pushed commit either deploys or fails loudly in a way that gets caught the same session, not silently ignored for another turn.
- **Fixed by**: `vercel.json`'s schedule changed to `0 0 * * *` (once daily, 00:00 UTC = 08:00 Asia/Manila - the real user's own configured timezone and T239's default `notification_time`). This restores normal deployments - commit `851eb32` is the one to confirm went green on Vercel.
- **Trade-off, explicitly accepted by the user (2026-08-04), not left open**: T239's whole point was a user-chosen delivery time, checked often enough (every 15 min) that any chosen time gets caught within a tight window. A once-a-day check can only catch a delivery time within ~20 minutes of whichever single UTC moment the cron fires - any other `notification_time` a user sets will now silently never send. Presented three options (an external free cron service hitting the route from outside Vercel's own Cron Jobs product and its plan limit; upgrading to Vercel Pro; accepting once-daily) - the user chose **accept once-daily for now**. Not tracked as a further follow-up task unless raised again; if the user later sets a `notification_time` far from 08:00 Asia/Manila expecting it to fire, that's this same known, accepted limitation, not a new bug.

### Bug #22 - An income row's "account balance after this" doesn't net out its own same-day auto-move, overstating what's left in the source account
- **Reproduce**: link an income to an account with an auto-move (T212) that sends 100% of that income to another account, on the same occurrence. Click the income's row in the Forecast table.
- **Reported** by the user 2026-08-04: "i have an auto move nanay hh going to bdo tatay for the entire amount, yet it says 'UB Nanay will be 67696.23 ₱ after this' despite sending the entire amount to BDO Tatay."
- **Confirmed exactly against real production data**: "Nanay - HH" (income, ₱44,000.00, connected to "UB Nanay") has one `income_auto_moves` rule sending the *full* ₱44,000.00 to "BDO Tatay." UB Nanay's real current balance is ₱23,696.23. Clicking the income's Aug 31 occurrence showed "₱67,696.23 after this" - exactly ₱23,696.23 + ₱44,000.00, i.e. the raw income credit with no allowance at all for the auto-move debit that fires alongside it.
- **Root cause**: `computeAccountBalancesAfterEachRow` (`src/lib/engine/accountBalances.ts`, T191) walks the forecast's rows in their final sorted order and records the connected account's balance immediately after each row. `forecast.ts` sorts same-day rows incoming-before-outgoing (T148) - an income row is incoming, its own hidden `income_auto_move` debit leg (T212/T214) is outgoing, so the debit *always* sorts after the income, no matter what else is on the same day. T214 deliberately hides the auto-move rows and presents them as a tag on the income's own row precisely so the user reads them as part of the same transaction - but the balance snapshot shown when clicking that row never reflected that framing; it showed the account's state one half-step into the transfer, not after it.
- **Expected**: the balance shown for an income with a same-occurrence auto-move already reflects that auto-move, since T214 presents it as inseparable from the income's own row.
- **Fixed by**: `computeAccountBalancesAfterEachRow` now separately indexes every `income_auto_move` row by `(linkedIncomeId, originalDate, balanceId)` and, only when recording an income row's own snapshot, folds in the net effect of any same-occurrence auto-move leg(s) hitting that row's own account - the underlying `current` running map used by every other row is untouched, so this doesn't change any other row's figure, the combined total, or `runningBalance` (Bug #19 already handles that correctly). 276/276 tests (2 new, reproducing the exact reported figures and confirming a plain income with no auto-move is unaffected), tsc, build, eslint clean.
- **The report's second half - GLoan's own "BDO Tatay will be ₱26,426.24 after this," expected higher given the ₱44,000 auto-move credit and GLoan's own ₱2,480.83 charge - was investigated and is very likely not a bug.** Confirmed against real data: BDO Tatay has upwards of 20 other real bills/debts connected to it with due dates scattered across the same month (Youtube, GLoan - Nanay, Internet, Claude Pro, iCloud, Juanhand - Nanay, Maya Loan - Nanay, both GGives - Nanay - S&R rows, GGives - Nanay, Loan - Car (Happy), LazPay, GLoan - Tatay, Electricity, Disney, Microsoft 365, Google, HBO, Netflix, Water, Helper - Jikay, Maya Credit - Nanay, GLoan - Tatay again and Juanhand also landing the same day as GLoan) - a rough hand-total of just the ones dated strictly before GLoan's own date already exceeds ₱121,000, far more than the ₱44,000 credited in. The fix above doesn't touch the running `current` walk any other row reads from, so it has no effect on this figure either way. Recommended next step: the user re-check this specific figure live in the app (not by hand) now that the confirmed bug above is fixed - if it still looks wrong once every other BDO Tatay transaction between today and that date is accounted for, reopen as its own bug with the exact two dates/items involved so it can be walked precisely rather than estimated.

### Bug #21 - Editing a forecasted transaction's connected account changes every future occurrence of that item, not just the one being edited
- **Reproduce**: on `/forecast`, click a recurring row (bill/income/debt/savings), open the Edit tab, change "Connected account," save. Check a *different* future occurrence of the same item.
- **Reported** by the user 2026-08-03: "editing an account in the forecast page edits all of the future transactions for that finance item. it should just update for that specific forecasted transaction and not the rest of that finance item's future transactions."
- **What happened**: every other occurrence of the item picked up the new account too - confirmed against real data (a test override on one occurrence of a real bill correctly showed the new account with the edited-pencil icon, while the item's other occurrences were unaffected only because the fix below writes to a different table entirely than the one T193 used to write to).

### Bug #19 - Forecast shows an inflated balance on the row right after an income-linked auto-move, when another same-day row lands between its two legs
- **Reproduce**: link an income to an account with an auto-move to another account (T212), on a day that also has another same-day bill/debt/savings/misc row connected to the *same source account*. Open `/forecast`.
- **Reported** by the user 2026-08-02: "in the aug 5 TTM income, when I put move 50k to BDO Tatay, it becomes a total income of 78k (TTM real income) to 128k (combines the auto move 50k, which should not)... the line after that (Lalens allowance) should just deduct 4k, but it instead adds the 50k then deducts the 4k."
- **What happened**: the Balance column on the row immediately following the income (a same-day bill) showed a figure inflated by the full auto-move amount, before dropping by its own amount - as if the transfer's ₱50,000 credit had landed but its matching ₱50,000 debit hadn't yet. **Confirmed against the real account already in use** (not just the user's report): Aug 8 - "Nanay - TNIT" (auto-moves ₱10,000 to BDO Tatay) showed ₱161,632.06, then "Claude Pro" (-₱1,300) showed ₱170,332.06 - higher than the income row despite being an outgoing bill, exactly ₱161,632.06 + ₱10,000 - ₱1,300. Same pattern on the Aug 15 occurrence against "Loan - Car (Happy)". This was already live in production before the user's newer TTM/50k test surfaced it.
- **Expected**: an internal transfer between two tracked accounts never changes the combined total, so no visible row's Balance column should ever reflect only one side of it.
- **Root cause**: `generateForecast` (`src/lib/engine/forecast.ts`) pushes a linked income's auto-move debit/credit pair into `rows` in its own loop, which runs *after* every bill/income/debt/savings/budget row has already been pushed. The final same-day sort only guarantees "incoming before outgoing" and is otherwise stable (array order breaks ties) - so any other same-day *outgoing* row (a bill, in the reports above) that was pushed earlier in the array stays sorted ahead of the transfer's debit leg, landing between the credit (already applied, since it's grouped with the other incoming rows) and the debit (still pending). The combined running balance sat inflated by the full transfer amount for every row in between.
- **Fixed**: the combined `runningBalance` reduce in `generateForecast` now excludes an `income_auto_move` row's `amount` entirely (contributing `0`) - the fee it may carry still applies, since that's a real cost leaving the tracked accounts, not part of the internal transfer. This makes the combined total immune to the pair's relative ordering, rather than relying on the two legs happening to land adjacent to each other. Per-account attribution (`accountBalances.ts`) is unaffected - it walks rows independently by `balanceId`/`amount`, never reads `runningBalance`, so each account's own projected balance is untouched by this fix. New regression test reproducing the exact reported shape (income + auto-move + a same-day bill) in `forecast.test.ts`; 245/245 tests, tsc, build, eslint clean. Verified against the real account before/after: the inflated intermediate figures above are now correct in the running dev server.

### Bug #18 - Budget account actions never show up in the Updates feed (real data, silent since T204)
- **Reproduce**: create, rename, or delete a budget account, or Add/Take/Move funds on one directly (Budgets page > Budget Accounts section). Check `/updates`.
- **Reported** by the user 2026-08-02: "the updates doesnt update when i update budget accounts in any way. every single action within the web app should have a corresponding update log."
- **What happened**: nothing about budget-account activity ever appeared in Updates, for any account, ever - confirmed against production: zero `entity_type = 'budget_account'` rows exist in `activity_log` despite the feature having been in daily use since T204 (2026-08-01).
- **Root cause**: T204/T209 added `'budget_account'` to the app-level `ActivityEntityType` union and correctly called `logActivity(..., entityType: "budget_account", ...)` from every budget-account action - but `activity_log`'s own DB-level `entity_type` CHECK constraint (migration 0029, written before T204 existed) was never updated to allow that value. Every one of those inserts has been rejected by Postgres since the day T204 shipped. `logActivity` deliberately never surfaces a logging failure to the user (a diary entry failing to write must not turn a successful create/edit/delete into a reported error) - but its `catch` block was also fully silent, with nothing printed anywhere either, so this went undetected for a full session's worth of real usage.
- **Expected**: every budget-account action logs to Updates, same as every other financial record type.

### Bug #14 - Settling an income linked to a budget double-counts the allocation (real money, live data)
- **Reproduce**: link a budget with an allocation (e.g. ₱1,000) to an income (e.g. ₱20,000). Settle one occurrence of that income with an account selected. Check the account balance and the budget's running total. Found 2026-07-31 while scoping the user's "20,000 income minus 1,000 budget = 19,000" request, which turns out to describe this bug rather than a missing feature.
- **What happened (traced in code, not yet confirmed against live data)**: the full ₱20,000 lands in the cash account *and* ₱1,000 lands in the budget ledger. The same ₱1,000 is now counted twice. Meanwhile the Forecast had already projected the ₱1,000 as a real deduction before settling (T59), so settling makes the actual balance land ₱1,000 *above* what the forecast promised - the opposite direction from Bug #11, and equally misleading.
- **Expected**: settling a ₱20,000 income with a ₱1,000 linked budget should put ₱19,000 in the cash account and ₱1,000 in the budget, matching what the Forecast projected.
- **Root cause (identified, not yet fixed)**: in `settleOccurrence` (`src/app/(app)/forecast/actions.ts`), the cash side is applied once, up front - `applyToBalance(supabase, fields.balanceId, actualAmount)` with the *full* income amount. The linked-budget loop further down (the `type === "income"` branch) then writes a `budget_entries` incoming row plus a `settlements` row carrying `actual_amount: -allocation`, and marks a `budget_replenish_overrides` skip - but it never calls `applyToBalance` again to take the allocation back out of the cash account. The settlement row records a cash effect that never actually happened. Dashboard/Forecast "Total Balance" is `balances.reduce(...)` over accounts only (budgets are deliberately not included), so nothing downstream corrects for it.
- **Confirmed by a second pass (2026-07-31)**: `applyToBalance` has exactly one call site in the whole codebase (line 182), always with the unmodified `actualAmount`; the only other writes to `balances.amount` are the manual create/edit/delete on the Accounts page. There is no compensating deduction anywhere. On the forecast side, `forecast.ts` does project the replenishment as "a bill-like row" against the running balance for any occurrence not yet settled or skipped, so the projection genuinely does promise the net figure.
- **Precision, in fairness to the report**: the cash account is only overstated when an account is actually selected at settle time (`fields.balanceId`). Settle with no account chosen and no balance moves at all, so nothing is double-counted there - but the forecast-versus-reality divergence still exists, because the projection assumed the allocation would leave. The user connects most items to accounts, so the first case is the likely one.
- **Measured against live production data** (read-only aggregates, 2026-07-31): 5 replenishment settlements between 2026-06-05 and 2026-07-29, totalling **₱26,000** overstated. Every linked income has an account set, so that is exact rather than an upper bound - GCash by ₱24,000 across 4 settles, BDO Tatay by ₱2,000 across 1.
- **Fixed by**: **T151** in SPEC.md Phase 20 - `settleOccurrence` now resolves the linked budgets before touching cash and applies `actualAmount - totalAllocation` in a single write. Netting rather than a second `applyToBalance` call is deliberate; see T151's write-up.
- **Historical balances were not corrected.** That means writing inferred amounts onto real money, so it stays the user's call - and roughly half the measured ₱26,000 turned out to be phantom, from leftover sample-data rows (**T170**) that need resolving first.

### Bug #11 - Forecast silently drops past-dated transactions that were never settled
- **Reproduce**: log a Misc (one-off) item dated yesterday or earlier and never settle it, then open `/forecast` the next day.
